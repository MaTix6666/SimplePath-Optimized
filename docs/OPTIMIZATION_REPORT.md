# SimplePath: оптимизированная сборка

**Что сделано.** Я взял [SimplePath](https://v3n0m-z.github.io/RBLX-SimplePath/) от @V3N0M_Z (лицензия MIT) и оптимизировал внутреннюю реализацию. **Публичный API не менялся**: `Path.new`, `Run`, `Stop`, `Destroy`, `GetNearestCharacter`, события `Reached`, `WaypointReached`, `Blocked`, `Error`, `Stopped`, поля `Status`, `LastError`, `Visualize`. В большинстве проектов модуль можно подменить без правки кода NPC.

---

## Что изменено

### 1. События без `BindableEvent`

Раньше на каждый путь создавалось 5 инстансов. Теперь используется лёгкий `Signal` на таблицах, а таблица обработчиков создаётся лениво.

```lua
-- было
_events = {
    Reached = Instance.new("BindableEvent");
    Error   = Instance.new("BindableEvent");
    -- ... ещё 3
}

-- стало
Reached = Signal.new();
Error   = Signal.new();
```

### 2. `GetWaypoints` вызывается один раз

Раньше дважды за успешный `Run`, причём первый вызов происходил прямо в проверке статуса.

```lua
-- было
or #self._path:GetWaypoints() < 2 ...        -- вызов 1
self._waypoints = self._path:GetWaypoints()  -- вызов 2

-- стало: только после проверок, один раз
waypoints = pathObject:GetWaypoints()
```

### 3. `SetNetworkOwner` один раз на PrimaryPart

Раньше вызывался при каждом `Run`, теперь результат запоминается.

### 4. Быстрый доступ к полям и методам

`__index` был функцией и срабатывал при каждом вызове метода, теперь это таблица.

```lua
-- было
Path.__index = function(table, index) ... end

-- стало
Path.__index = Path
```

### 5. Мелочи

- квадрат расстояния через `Dot` вместо `Magnitude`;
- `pcall(func, args)` без создания замыканий;
- типизация и `--!native`.

## Результаты

**Условия теста:** 110 препятствий на карте, NPC пересчитывают путь каждые 0.25–0.6 с, по 30 секунд на этап, одинаковые позиции спавна, один прогон в Studio.

### Нагрузка скриптов на сервере

| Нагрузка | Старый модуль | Новый модуль |
|---|---|---|
| 100 NPC | 4.6–6.1%, обычно ~5% | 3.2–4.6%, обычно ~4% |
| 200 NPC | 8.5–9.6%, обычно ~8% | 7.7–8.5%, обычно ~7% |

Это около 1 процентного пункта: примерно 20% снижения на 100 NPC и 12% на 200 NPC (от нагрузки скриптов).

### Объём выполненной работы (поведение идентично)

| Метрика | Старый | Новый |
|---|---|---|
| 100 NPC, вейпоинтов в секунду | 313 | 313 |
| 100 NPC, пересчётов пути в секунду | 193.8 | 192.8 |
| 200 NPC, вейпоинтов в секунду | 622 | 626 |
| 200 NPC, пересчётов пути в секунду | 370.9 | 373.6 |

Оба модуля выполняют одинаковую работу, то есть новый ведёт себя так же, как старый.

### Сырой вывод теста

```
[Старый модуль | 100 NPC] cpu=0.45ms frame=9.20ms p99=14.0ms fps=109.1 mem=+0.2MB inst/npc=71.6 waypoints/s=313 repaths/s=193.8
[Старый модуль | 200 NPC] cpu=1.00ms frame=13.13ms p99=18.0ms fps=76.4 mem=+0.4MB inst/npc=71.0 waypoints/s=622 repaths/s=370.9
[Новый модуль  | 100 NPC] cpu=0.44ms frame=8.96ms p99=14.0ms fps=112.0 mem=+0.1MB inst/npc=71.0 waypoints/s=313 repaths/s=192.8
[Новый модуль  | 200 NPC] cpu=1.00ms frame=13.23ms p99=19.0ms fps=75.7 mem=+0.4MB inst/npc=71.0 waypoints/s=626 repaths/s=373.6
```

## Честные оговорки

- Выигрыш скромный: основную работу делает `ComputeAsync`. Он нативный и в обоих вариантах одинаковый.
- Тест прогнан один раз, новый модуль шёл вторым, поэтому эффект порядка (разогрев, кэши) не исключён. Измерения проводились в Studio.
- Разница в среднем кадре (9.20 против 8.96 мс и 13.13 против 13.23 мс) и в памяти (+0.2 против +0.1 МБ) укладывается в шум.
- Снижение числа инстансов на NPC не измерено и не заявляется (`inst/npc` одинаков у обоих модулей).
- Метрика CPU Heartbeat не показала разницы (0.45 против 0.44 мс и 1.00 против 1.00 мс), потому что она учитывает не всю работу скриптов. Основная цифра выигрыша взята из замера нагрузки скриптов на сервере.

## Что может потребовать правки при замене

| Ситуация | Что делать |
|---|---|
| Чтение приватных полей `_status`, `_events`, `_lastError` | Использовать `Status` и `LastError`; `_events` и `_position` удалены |
| Janitor, Maid, Trove: события теперь не `RBXScriptSignal` | Добавить в модуль алиас `Connection.Destroy = Connection.Disconnect` |
| Проверка `typeof(path.Reached) == "RBXScriptSignal"` | Убрать или заменить проверкой на `:Connect` |
| Код рассчитывает на мгновенный вызов обработчиков при `SignalBehavior = Immediate` | `Signal` всегда откладывает вызов через `task.defer`, учесть при логике |
| Событие `Stopped` | Теперь передаёт `agent` (раньше из-за опечатки передавался `nil`) |
| `SetNetworkOwner` отдавался игроку и ожидалось, что `Run` вернёт его серверу | Теперь `Run` делает это один раз на PrimaryPart, вернуть владение нужно вручную |

Быстрая проверка: поиск по всем скриптам игры по строкам `_status`, `_events`, `_lastError`, `_position`, а также `typeof(` рядом с путями. Если находок нет, замена безопасна.

Заодно исправлено: `GetNearestCharacter` больше не падает на персонаже без PrimaryPart, а `Blocked` до первого `Run` больше не вызывает ошибку.

## Установка

1. Удалите старый модуль.
2. Положите новый с **тем же именем** и в то же место, откуда его берут через `require`.
3. Делайте замену до запуска NPC: уже запущенные скрипты держат старую версию в кэше `require` до перезапуска сервера.

Менять вызовы и логику у самих NPC не нужно.

## Как воспроизвести тест

В проект добавлены кнопка `Workspace.StressTestButton`, контроллер `ServerScriptService.StressTestController` и интерфейс `StarterPlayerScripts.StressTestUI`.

Порядок: прогрев 8 с (в зачёт не идёт), затем старый модуль на 100 и 200 NPC, затем новый на 100 и 200 NPC. Каждый этап 30 с, между этапами перерыв 3 с. Запуск: нажать `E` у зелёной кнопки или кликнуть по ней. Итоги выводятся в интерфейс и в Output.
